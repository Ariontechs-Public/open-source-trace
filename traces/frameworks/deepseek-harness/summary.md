# DeepSeek Harness

## TL;DR
DeepSeek Harness (`dsh`) is DeepSeek AI's open-source agent harness, and its one architectural bet is that **everything is a plugin** — the model adapter, the tool registry, the session log, the web UI, and the agent loop itself are all plugins mounted on a shared [Cordis](https://github.com/cordiverse/cordis) context. There is no privileged core to patch: you extend dsh by mounting a plugin beside the others, and every registration is a reversible effect that unwinds when its plugin unloads. A running `dsh` is a plugin tree composed at boot from ordered layers (profile → bundles → patch files), so any row of that tree can be replaced from configuration. Holding it all together is one hard invariant — **model-visible ⟺ logged**: anything that reaches a model request must be reconstructable from the append-only session log, asserted at runtime. 219 packages, ~302k LOC of TypeScript against ~263k LOC of tests, built in roughly two months (12,293 commits, June–August 2026), currently `0.1.0-rc.5` with no compatibility promises.

**中文口訣**: 萬物皆插件、連 agent loop 也是——沒有可修改的核心,只有可替換的層;而且**模型看得到的,一定寫進 log**。

## Why I Care
This is the reference implementation of the question I keep hitting: *when a harness needs a new capability, where does it go?* dsh's answer is a documented extension-point table instead of a growing `if` in a loop, and it pays for that answer with real machinery — a role triad for every capability seam, typed events with declared dispatch modes, and a boot-time patch stack. It's also the most complete example I've seen of an **agent-authored design record system** (`.agents/notes/`, 684 bilingual RFCs with machine-checked lifecycle and a frozen archive), which is directly relevant to how I structure docs for agents in my own repos. And it interoperates rather than competes: it speaks Claude Code's and Codex's hook protocols and can delegate a subagent turn to either of them.

## Killer Ideas
- **The loop is a plugin, so extending the harness never means editing the loop.** `core/agent-loop` is one implementation of the `Agent` interface registered on `ctx.agentLoop`; `docs/architecture.md` carries a "where new behavior goes" table mapping ~20 goals to their extension points, and the convention is explicit: *"Plugins, not loop changes — changing `agent-loop` requires updating docs/architecture.md."*
- **Model-visible ⟺ logged.** The session log is the source of the context the model sees; `deriveMessages()` projects model history from it, and raw `assistant/chunk` events are kept so replay and UI fidelity survive. A new model-visible input therefore *requires* a new `SessionEventMap` member — there is no side channel. This kills the whole class of "the agent behaved differently on resume" bugs by construction.
- **The input queue is event-sourced too.** `Inbox` ([packages/core/agent/src/inbox.ts](../../../frameworks/deepseek-harness/packages/core/agent/src/inbox.ts)) is a replay-once projection over durable `agent/inbox/spliced` events with two lanes — `next-turn` for queued prompts, `next-step` for steering and injected context. Steering isn't ad-hoc mutation of a live queue; it's a logged splice with normalized coordinates.
- **A capability seam is a mandatory role triad**: Service Definition / Service Provider / Consumer. "A package may combine roles, but one role alone is not a seam." The payoff is compositional: fs and subprocess providers share one execution world, so repointing them at a remote sandbox moves Bash, PTY, and LSP with them — no provider forks.
- **Composition as a patch stack, not a config file.** A *profile* stacks *bundles* (`dsh-base` → `dsh-web-app`/`dsh-headless`), then the profile's `cordis.patch.yml`, then the home-level one, then `--patch`. `dsh --profile web --dump-config` prints the tree your machine actually boots, and every row it prints is addressable by id and replaceable.
- **The agent can rewrite its own runtime.** `cordis_inspect` / `cordis_mount` / `cordis_unmount` ([packages/extensions/tool-cordis](../../../frameworks/deepseek-harness/packages/extensions/tool-cordis)) let the model enumerate live services and events, then mount a model-written plugin — registering *new tools* — into the process it is running in, evaluated in a `node:vm` realm and disposable to quiescence. The design note is refreshingly honest that this is bash-equivalent trust, not a sandbox.
- **`.agents/notes/` — RFCs written by agents, enforced by gates.** 684 notes at `{lifecycle}/{class}/yyyy-mm-dd-topic.md`; every non-trivial PR must add or update one; `## Alternatives considered` is mandatory ("a decision recorded without what it beat invites re-litigation"); every note has a `.zh.md` counterpart plus a hash sidecar; archived notes are frozen by an append-only manifest and may never be edited or cited as current authority. Deliberately **no index file** — the folder tree *is* the inventory.
- **Interop over displacement.** `hooks-claude-code` / `hooks-codex` implement their hook wire protocols; `subagent-claude-code` / `subagent-codex` / `subagent-acp` delegate a subagent turn to another product behind one interface; there's a skill provider registry and an ACP server. dsh assumes the ecosystem around it already exists.
- **Documentation as a build artifact.** `docs/config-catalog.md` (129K), `tool-catalog.md` (79K), `module-graph.md` (122K), and `persistence-catalog.md` (33K) are all generated, and `pnpm run doc-sync` regenerates them in memory and fails on any diff — a JSDoc edit cannot ship without regenerating the catalog the model reads.

## Open Questions
- What is the real cost of the invariant? "Model-visible ⟺ logged" plus durable `assistant/chunk` events means every token streamed is an appended event — what does the JSONL/SQLite session log weigh after a long coding session, and where does the spill/compaction seam (`packages/spill`, `packages/compaction`) actually kick in?
- Cordis's `inject`-based activation replaces manual boot ordering — but what does a *misconfigured* tree look like in practice? A pending plugin silently waiting on a service that never arrives is the classic DI failure mode; `misconfiguration fails loud` is the stated rule, but I haven't traced how a missing provider surfaces.
- Per-file 100% coverage on `packages/*/*/src` is an unusually absolute gate. What does the exemption list (`scripts/coverage-exempt.ts`) actually contain, and does the 263k LOC of test code buy real confidence or mostly satisfy the gate?
- Is the agent-note system transferable, or does it only work at DeepSeek's authorship density? 684 notes in ~2 months implies notes are being written by the agents doing the work — I want to see the `dsh-code-review` / `dsh-archive-agent-notes` skills to understand who actually writes and prunes them.
- `packages/workflow` ships `tool-workflow` and `tool-ralph` with a worker-thread engine exposing `parallel()`/`pipeline()` hooks — nearly the same shape as Claude Code's Workflow tool. Convergent design, or direct influence?
- How much of the 219-package split is genuine seam discipline versus packaging overhead? `subagent/` alone is 11 packages.
